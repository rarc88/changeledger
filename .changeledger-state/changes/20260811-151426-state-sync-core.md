## Request

Etapa 3 del estado global, con las restricciones fijadas por el humano
(2026-08-11): la sincronización nunca es bloqueante, es desacoplada y
agnóstica del proveedor; sin remoto o sin red, todo el flujo local avanza
igual. `sync` SIEMPRE compara el local con el remoto primero: si el local
puede actualizarse de manera segura, se actualiza y después se pushea lo
propio; si no, se reporta el conflicto y la resolución precede al push.
Expectativa de uso: cada persona trabaja en su change, así que los journals
divergentes normalmente tocan documentos disjuntos y deben reconciliarse
solos; el caso probable de colisión real son las graduaciones concurrentes
sobre la MISMA spec.

## Investigation

- La ref de estado vive en `refs/heads/changeledger/state` (etapa 1):
  namespace de branch normal, así que `git fetch`/`git push` estándar la
  transportan sin adaptadores — provider-agnostic por construcción.
- La activación (`refs/changeledger/activation`) es una decisión del
  checkout local (ancla `ledger_dir`) y NO se sincroniza: cada clon activa
  el suyo con `changeledger activate` contra la ref ya traída.
- El journal es append-only por CAS (`mutateState`, `update-ref` con
  old-value): un fast-forward local es un CAS más; una reescritura del
  journal remoto o local está excluida — la reconciliación de divergencias
  se materializa como commit nuevo que preserva ambos padres, nunca como
  rebase.
- `readSnapshot` lee el árbol en cualquier revisión; comparar dos tips y su
  merge-base por documento es `treeEntries` sobre tres revisiones — las
  primitivas existen (`src/git-batch.mjs`).
- El techo (`global-state-scope`) fija: sync git puro, opcional,
  best-effort; nunca resolución multi-fuente automática de CONFLICTOS —
  reconciliar documentos disjuntos no resuelve ningún conflicto, es unir
  historias que no chocan; el conflicto real (mismo documento, contenido
  distinto) siempre para al humano.
- Los "proveedores" son documentación de branch protection, nunca
  adaptadores en código (decisión del plan v3, 2026-08-08).

## Proposal

Un comando nuevo, `changeledger sync [--status]`, git puro sobre el remoto
ya configurado del repo:

- **Comparar primero, siempre:** fetch de la ref remota; con la copia
  remote-tracking fresca se clasifica la relación local↔remoto en uno de
  cuatro estados: idéntico (no-op), remoto delante (fast-forward local por
  CAS), local delante (push), divergencia (ambos avanzaron).
- **Divergencia con documentos disjuntos = actualización segura:** se
  computa el diff por documento de cada lado contra el merge-base; si los
  conjuntos de rutas cambiadas no se intersectan, se construye el árbol
  unido y se aterriza como UN commit de reconciliación con ambos padres
  (los dos journals se preservan íntegros), CAS sobre la ref local, y
  después push. Un documento cambiado igual en ambos lados (byte-idéntico)
  no es colisión.
- **Colisión de mismo documento = conflicto, nada se escribe:** el reporte
  nombra cada documento en colisión con ambos tips, distingue el caso specs
  (graduaciones concurrentes — el caso probable declarado) y termina con
  exit distinto de cero. La resolución la coordina el humano según el
  protocolo del contrato; tras resolver, `sync` reanuda (actualiza y
  pushea).
- **Nunca bloqueante, desacoplado:** sin remoto configurado o sin la ref
  remota, no-op informativo con exit 0; un fallo de red es aviso, no error
  del flujo; ningún otro comando consulta ni espera a `sync`.
- **La activación no viaja:** es la decisión local de cada checkout (el
  ancla de propiedad); en un repo con la ref presente pero sin activar,
  `sync` es no-op informativo que nombra `changeledger activate` — el paso
  manual único por clon nunca es invisible, y un fetch jamás cambia el modo
  de operación de un repo por sí solo.
- **`--status` es offline:** reporta ahead/behind contra la copia
  remote-tracking del último fetch sin ejecutar ninguna operación de red,
  para que cualquier punto del flujo pueda medir frescura gratis.

Alternativas descartadas: sync automático en transiciones del flujo
(acopla mutaciones locales a la red y es automatización oculta — no-goal de
INTENT; una transición esperando un fetch es bloqueo); rebase/replay del
journal local sobre el remoto (reescritura de historia publicada: rompe el
CAS de cualquier otro clon); resolución automática de colisiones de mismo
documento (excluida por el techo — conflicto → humano); adaptadores por
proveedor (los "proveedores" son docs).

Escenarios: clon que solo consume (fast-forward); autor único que publica
(push); dos autores en changes distintos (reconciliación disjunta
automática + push); dos graduaciones concurrentes de la misma spec
(conflicto nombrado, resolución, push); repo sin remoto (no-op exit 0);
sin red (aviso, flujo intacto); `--status` tras días sin fetch.

## Specification

### CR1 — El remoto delante avanza el local de forma segura
- **Given** un clon activado cuya ref remota avanzó linealmente (el tip local es ancestro del remoto)
- **When** se ejecuta `changeledger sync`
- **Then** la ref local queda fast-forward en el tip remoto vía CAS, `list` sirve los documentos nuevos y no se pushea nada

### CR2 — El local delante publica
- **Given** un repo activado cuyo journal local avanzó y el remoto no se movió
- **When** se ejecuta `changeledger sync`
- **Then** la ref remota queda en el tip local (verificado en el remoto de fixture) y el journal local no gana ningún commit

### CR3 — La divergencia disjunta se reconcilia sola y se publica
- **Given** dos clones que avanzaron sus journals tocando conjuntos de documentos disjuntos respecto del merge-base
- **When** se ejecuta `changeledger sync` en uno de ellos
- **Then** la ref local queda en un commit de reconciliación con ambos padres cuyo árbol contiene los cambios de los dos lados íntegros, se pushea, y el otro clon queda fast-forward con su siguiente `sync`

### CR4 — La colisión de mismo documento para al humano
- **Given** dos clones cuyas divergencias editaron el MISMO documento con contenido distinto — cualquier documento del ledger: el caso más probable es la misma spec por graduaciones concurrentes, pero un change compartido colisiona igual
- **When** se ejecuta `changeledger sync`
- **Then** no se escribe nada en ninguna ref, el reporte nombra cada documento en colisión con ambos tips distinguiendo su clase (change o spec), y el exit es distinto de cero
- **And** un documento cambiado byte-idéntico en ambos lados no cuenta como colisión

### CR5 — Sin remoto o sin red, el flujo no se entera
- **Given** un repo activado sin remoto configurado, y otro con remoto pero sin red (URL inalcanzable)
- **When** se ejecuta `changeledger sync`
- **Then** el primero es no-op informativo con exit 0; el segundo reporta el fallo de red como aviso sin tocar ninguna ref; y ningún otro comando del CLI cambia de comportamiento en ninguno de los dos
- **And** un repo inactivo con la ref presente recibe un no-op informativo que nombra `changeledger activate`, sin activar nada por sí solo

### CR6 — El status es gratis
- **Given** un repo activado con copia remote-tracking de un fetch anterior
- **When** se ejecuta `changeledger sync --status`
- **Then** reporta la relación local↔remote-tracking (idéntico/delante/detrás/divergente) sin ejecutar ninguna operación de red (verificado contando subprocesos git de red)

### CR7 — Primer uso end-to-end
- **Given** ESTE repo activado con su remoto real y un clon fresco
- **When** se pushea la ref con `sync`, el clon la trae, activa, muta su journal con un change nuevo y ambos lados ejecutan `sync`
- **Then** ambos sirven el mismo `list --all` byte a byte, con la reconciliación pasando por los caminos de CR1-CR3 según toque
